## 1. 判定シートの生成

```bash
cd SurveyProtocol
python -X utf8 scripts/make_screening_sheets.py
```

続けて、評価者が実際に記入する Excel 版を作る:

```bash
python -X utf8 scripts/make_screening_xlsx.py
```

出力（`screening/`）:

| ファイル | 内容 | 誰が触るか |
|---|---|---|
| `assignment.csv` | 割当の正（record_id・block・担当2名） | **編集しない** |
| `sheet_<id>.csv` | 生成時の雛形（機械可読の正） | 触らない |
| **`sheet_<id>.xlsx`** | **各評価者の作業ファイル** | 本人のみ |

**評価者に配るのは `.xlsx` の方**。集計スクリプトは同名の xlsx があればそちらを
優先して読むので、CSV は雛形として残しておいてよい。

### Excel 版に入れてある補助

| 機能 | 目的 |
|---|---|
| 判定列のドロップダウン（Include/Exclude/Unsure） | 表記ゆれを構造的に防ぐ。集計時の不正値がゼロになる |
| 見出し行＋ID列の固定 | 横スクロールしても列の意味と対象を見失わない |
| オートフィルタ | 「判定が空白」で絞れば未記入だけ表示できる |
| 要旨欠落行の淡い赤 + `要旨有無` 列の `N` | **色だけに意味を持たせない**。フィルタでも絞れる |
| Exclude なのに理由が空のセルを赤字強調 | 提出前の自己チェック |
| 記入3列以外をロック | 誤編集の防止（パスワードなし。行・列幅の変更と並べ替え・フィルタは許可） |
| 見出しのコメント | 各列の意味を別紙なしで確認できる |
| 「はじめに」シート | 手順・判定の考え方・要旨の全文表示方法 |

> **要旨の表示について:** 要旨は中央値1,278字あり、セルに全文を収めると1行が15行分の
> 高さになって走査できなくなる。既定は「タイトル全文＋要旨の冒頭5行」が見える高さ（85pt）に
> しており、全文を読むときは行の高さの自動調整か数式バーの拡張を使う。手順は
> 「はじめに」シートに書いてある（行の書式変更はシート保護から除外済み）。

> **既存シートは上書きされない。** 記入途中で再生成しても作業は消えない
> （存在するファイルはスキップされる）。コーパスが変わって作り直したい場合は、
> 旧シートを退避してから実行すること。

### なぜ評価者ごとに別ファイルなのか

二重スクリーニングの妥当性は **評価者が互いの判定を見ないこと** に依存する。
1枚のシートに両者の列を並べると、先に書いた側の判定が後の側から見えてしまい、
独立性が壊れて κ が意味を失う。**他人のシートは開かないこと。**

## 2. 記入のしかた

各自、自分の `sheet_<id>.csv` の以下2列を埋める。

| 列 | 記入内容 |
|---|---|
| `decision` | `Include` / `Exclude` / `Unsure` のいずれか（大文字小文字は問わない） |
| `reason` | **Exclude のときは必須**。抵触した PICOS 基準を書く（例: `P: 患者対象`、`S: ユーザー実験なし`） |
| `note` | 任意。協議で持ち出したい論点など |

### 判定基準

`rule.md` の PICOS を **Title/Abstract レベルに緩めたもの**で判定する。

- **除外できると確信できないものは残す**（Include 側に倒す）。全文を読めば分かることを
  この段階で切らない。
- 迷ったら `Unsure`。Unsure は協議対象になるので、無理に二択にしない。

### 参考列（判定には使わない）

| 列 | 意味 |
|---|---|
| `kw_groups` | Rev.6 統合クエリの3概念群が Title+Abstract にいくつ成立するか（0〜3）。**読む順序のトリアージ専用**。シートはこの降順→新しい年順に並べてある。この値で機械的に除外してはならない |
| `has_abstract` | `N` は**要旨が無くタイトルだけで判定することになる**文献 |
| `rank` | 掲載先の CORE/SJR ランク。Phase 2 で既に基準を満たしているので、判定材料にはしない |

> ⚠️ **要旨欠落 170件（21.4%）** — Rev.13 で重複コピーからのマージにより大幅に回収したが、
> どのコピーにも要旨が無いものが残っている。これらは Phase 1.5 で `hold`（判定不能）として
> 保留されたレコードで、**タイトルのみでの判定**になる。無理なら `Unsure` にして協議に回すこと。
> 件数は Threats to Validity に明記する。

## 3. 集計と協議

全員の記入が終わったら:

```bash
python -X utf8 scripts/score_screening.py
```

出力されるもの:

1. **記入状況の検査** — 未記入・不正値・担当外レコード・Exclude なのに reason が空、を検出
2. **ペアごとの Cohen's κ とその平均**（3カテゴリ版が主報告。Unsure→Include に寄せた
   2カテゴリ版も参考として併記される。どちらを本文に載せるかは著者が決めるが、
   **両方を出したうえで選ぶ**ことで恣意的に見えないようにしている）
3. `screening/consensus_worklist.csv` — 不一致と Unsure だけを抜いた協議リスト

協議リストの `final_decision` と `consensus_note` を協議で埋める。

> **協議で解決しない場合は `Include` に倒して Phase 4 へ送る**（再現率優先、
> `rule.md` Phase 3b）。その場合は `consensus_note` に「協議で解決せず → Include」と
> 明記すること。後から件数を数えられる状態にしておく。

再度 `score_screening.py` を実行すると、未解決がゼロなら
`screening/final_decisions.csv`（最終判定）が生成される。Include のものが Phase 4 へ進む。

## 4. 報告に必要な数値

PRISMA / 本文に載せるため、以下を `score_screening.py` の出力から転記する。

- ペア別 Cohen's κ（3本）とその平均、Landis & Koch の解釈
- 一致件数 / 要協議件数（不一致・Unsure の内訳）
- 協議で解決した件数 / 解決せず Include に倒した件数
- Phase 3b の Include 件数（= Phase 4 の対象）と Exclude 件数

`screening/` 一式（割当・各評価者のシート・協議リスト・最終判定）は
**監査可能性のため supplementary material として公開する**。

> **バージョン管理での扱い（注意）:** 各評価者のシート `sheet_*.csv` / `sheet_*.xlsx` は
> **記入中は `.gitignore` で追跡しない**。3人分がリポジトリに入ると互いの判定が
> 見えてしまい、独立性が壊れるため。ただしこれらは `rule.md` が要求する監査証跡でも
> あるので、**スクリーニング完了後に `git add -f screening/sheet_*.csv` で必ず
> 追跡に加える**こと。割当表・協議リスト・最終判定は最初から追跡している。

## 5. 既知の制約

- **要旨欠落 170件** は上記のとおり。どのコピーにも要旨が無いレコード（Phase 1.5 の `hold`）
- 判定は人間の主観に依存する。緩和策は二重評価・κ の報告・協議記録の公開だが、
  主観であること自体は消えない（Threats に明記済み）
- `kw_groups` によるトリアージは読む順序を変えるだけで、判定対象は全件のまま。
  **順序が判定に与える影響（先に読んだものほど厳しく/甘くなる等）は統制していない。**
  これも Threats の候補
